# SYSTEM PROMPT: Build the "Vendor Signal Monitoring & Patch Engine" (Self-Updating APIs)

## SYSTEM OVERVIEW & GOAL
Build an open-source, automated API maintenance system ("Dependabot for API Breaking Changes & Model Deprecations"). 
The system operates on a **Static Community Registry Architecture (Approach A)** with a **Hybrid Enterprise Opt-In Mode**:
1. A central, serverless cron job fetches upstream vendor changes (OpenAI, Stripe, etc.), standardizes them into a unified `registry.json` file, and publishes it to GitHub Pages/CDN.
2. A downstream CLI / GitHub Action runs inside consumer codebases. It fetches `registry.json`, performs AST/regex scans for deprecated patterns or model IDs, applies codemods/patches, runs local test suites, and opens fully passing Pull Requests.

---

## IMPLEMENTATION STEPS

### STEP 1: Implement the 5 Central Signal Ingestion Workers
Create modular worker scripts inside the central registry repo (`vendor-signal-registry`):

1. **`OpenAPIDiffWorker`**:
   - Clone / fetch the official target vendor OpenAPI repo (e.g., `github.com/openai/openai-openapi`).
   - Run `oasdiff` against the latest commit or release tag vs. the previous tag.
   - Extract removed endpoints, renamed query/body parameters, and modified schema types.

2. **`DeprecationScraperWorker`**:
   - Scrape HTML/JSON from `platform.openai.com/docs/deprecations` (or equivalent vendor pages).
   - Extract structured metadata: `legacy_pattern` (e.g., `"gpt-4-0613"`), `replacement_pattern` (e.g., `"gpt-4o"`), `shutdown_date` (e.g., `"2026-10-23"`), and `severity` (`CRITICAL` vs. `WARNING`).

3. **`ModelPollingWorker`**:
   - Issue a scheduled `GET https://api.openai.com/v1/models` request using a free/low-cost central API key.
   - Compare the current model list against the previous state snapshot (`.models-snapshot.json`).
   - Flag models that disappeared or were newly marked as deprecated without explicit changelog entries.

4. **`ChangelogParserWorker`**:
   - Fetch RSS/Atom feeds and HTML changelogs (e.g., OpenAI Developer Changelog).
   - Pass raw text blocks to a fast LLM parser (e.g., `gpt-4o-mini`) to extract signature changes (e.g., `max_tokens` -> `max_completion_tokens`).

5. **`SDKReleaseWorker`**:
   - Listen to release webhooks/tags on official client SDKs (e.g., `openai/openai-python`, `openai/openai-node`).
   - Detect major semver version bumps or `-rc` tags (e.g., `v0.x` -> `v1.0` major architectural migrations).

STEP 3: Central Registry Build & Distribution Pipeline
Set up a GitHub Actions workflow in the central registry repo scheduled to run every 6 hours (cron: '0 */6 * * *').

Execute all 5 workers, validate the output against schema.json, and generate the fresh registry.json artifact.

Commit and publish registry.json to GitHub Pages / static CDN endpoint (https://your-org.github.io/vendor-signals/registry.json).

STEP 4: Build Downstream Scanner CLI / GitHub Action
Develop a lightweight local CLI tool (vendor-patch-cli) that runs inside target repositories:

Execution Modes:

Default Mode (Approach A): Download https://your-org.github.io/vendor-signals/registry.json over HTTP.

Hybrid Opt-In Mode (Approach B): If --custom-endpoint <url> is passed, bypass the remote central registry and query an internal/on-premise gateway endpoint directly (e.g. http://internal-gateway/v1/models).

Codebase Scanning Engine:

Parse project files (.py, .ts, .js, .env*, .yaml).

Use AST parsers (tree-sitter or native language AST tools) combined with regex line scanners to locate occurrences of affected_pattern.

Filter out false positives by verifying import contexts (e.g. confirming the string is used in an OpenAI client context or API config setting).

STEP 5: Build Code Modder & Patch Engine
When a matching deprecation/breaking change is found in the target repository:

Simple Replacements: Execute exact string & regex replacements for model IDs, environment variables, and config keys.

AST Codemods: Execute structural refactoring (e.g., renaming function parameters or transforming global static calls to instantiated SDK client instances).

Dependency Updates: Update package.json / requirements.txt / pyproject.toml if an SDK version bump is required.

STEP 6: Test Verification & Self-Correction Agent
Automatically run the project's native unit/integration test suite (pytest, npm test, jest, go test).

If tests pass: Proceed directly to PR generation.

If tests fail:

Capture stdout / stderr error traces.

Pass the failing test code, error log, and the registry.json migration rule context to a lightweight LLM agent.

Let the LLM adjust test mocks, fixture data, or response structure assertions to match the updated API spec.

Re-run tests (up to 3 retry loops).

STEP 7: PR Generation Module
When all tests pass, stage the modified files, create a new branch (auto-fix/openai-migration-<event_id>), push, and open a Pull Request:

Title: [Auto-Fix] Migrate deprecated OpenAI model "gpt-4-0613" -> "gpt-4o"
